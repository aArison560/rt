1. Pourquoi coller une image ?

fait — détaillé
Après les UV (où) vient la quoi · Hit u/v include/core/Object.hpp:5

L'étape 1 a prouvé que chaque point 3D sait dire (u, v) ∈ [0,1)² (sphère = longitude×latitude, plan = projection, tube = angle×hauteur). Le damier calculait la couleur par une formule. L'image fait la même chose en lisant un tableau de pixels :

\(\text{couleur}(P) = \text{tex}(\underbrace{u(P), v(P)}_{\text{étape 1}}, \underbrace{\text{pixels}[w \times h]}_{\text{étape 2}}).\)
Étape 1 (checker)Étape 2 (image)
base = ((⌊u·s⌋+⌊v·s⌋) mod 2) ? albedo2 : albedobase = map->sample(u, v) (pixels 0–255)
Preuve que les UV sont justesRéutilise les mêmes UV — zéro changement géométrie
2 couleursMillions de couleurs, mêmes équations d'éclairage
Idée clé : le Renderer ne change pas de maths d'éclairage — seule la ligne qui choisit base change. C'est pour ça que l'image suit automatiquement les objets en translation/rotation : les UV sont relatifs à l'objet, l'image ne fait que les habiller.

2. stb_image : le décodeur single-header

fait — détaillé
include/stb/stb_image.h (v2.30) · src/core/Texture.cpp:1

2.1. Principe

stb_image.h (≈277 Ko) décode PNG, JPG, BMP, TGA, PPM en un appel. Règle d'or du single-header : le .h déclare partout, un seul .cpp définit l'implémentation :

#define STB_IMAGE_IMPLEMENTATION  // 1 seule fois, ici :
#include "stb/stb_image.h"        // src/core/Texture.cpp:4-5

Le mettre dans deux .cpp = symboles dupliqués au link. Le mettre nulle part = undefined reference to stbi_load.

2.2. Chargement forcé RGB

unsigned char* px = stbi_load(path.c_str(), &w, &h, &n, 3); // 3 = force RGB
if (!px || w <= 0 || h <= 0) return false;
data.assign(px, px + (size_t)w * h * 3); // copie vers vector
stbi_image_free(px);                     // libère le malloc interne

Forcer 3 canaux simplifie tout : pas de cas PNG gris (1 canal), RGB (3) ou RGBA (4) — le sampler lit toujours des triplets. Le vector<unsigned char> possède ensuite les pixels (RAII : Scene::clear() libère via shared_ptr, aucun new nu). Fichier absent ou corrompu → load() rend false → le parser refuse la scène avec numéro de ligne au lieu de rendre du magenta silencieux.

Coût : une image 256×256 = 196 Ko RAM. Chargée une fois au parsing, partagée par tous les pixels via shared_ptr — le rendu multi-thread ne fait que lire, aucun verrou.

3. ImageTexture : sampler2D + repeat/clamp

fait — détaillé
include/core/Texture.hpp:1 · src/core/Texture.cpp:38

3.1. Structure

enum class TexWrap { Repeat=0, Clamp=1 };
class ImageTexture {
  int w=0, h=0; TexWrap wrap = Repeat;
  std::vector<unsigned char> data; // RGB, w*h*3
  Vec3 sample(double u, double v) const; // 0-255
};

3.2. Wrap : que faire hors [0,1] ?

Les UV des caps et des surfaces infinies peuvent déborder (ex. fract plan, v hyperboloïde infini). Deux conventions Blender :

\(\text{Repeat} : u \mapsto u - \lfloor u \rfloor\) (tuilage infini) — \(\text{Clamp} : u \mapsto \min(\max(u,0),1)\) (bords étirés).
Testé : repeat(1.2) == repeat(0.2) ✓, clamp(1.5) == clamp(1.0) ✓.

3.3. Échantillonnage + flip V

double uu = wrapCoord(u, wrap), vv = wrapCoord(v, wrap);
vv = 1.0 - vv;                    // stb : ligne 0 en haut ; UV : origine en bas (Blender)
int x = uu * w, y = vv * h;       // plus proche voisin (pas de filtrage bilinéaire)
return Vec3(data[(y*w+x)*3], data[(y*w+x)*3+1], data[(y*w+x)*3+2]);

Sans le flip, l'image apparaît à l'envers (ciel en bas). Le plus proche voisin est volontaire : simple, rapide, et le moiré lointain reste un aliasing attendu — le filtrage bilinéaire sera une optimisation, pas un correctif.

4. Material + Renderer : priorité image

fait — détaillé
include/core/Material.hpp:14 · src/core/Renderer.cpp:17

4.1. Extension du Material

struct Material {
  // ... albedo, albedo2, useChecker, uvScale (étape 1, inchangés)
  std::shared_ptr<ImageTexture> map = nullptr;
  bool useImage = false; // prioritaire sur checker si actif
};

shared_ptr (pas unique_ptr) : la texture est créée au parsing puis copiée avec Hit::material à chaque intersection — le compteur partagé garde les pixels vivants tant qu'un objet ou un hit les référence. class ImageTexture; en forward-declaration dans le header évite d'inclure stb partout (temps de compile).

4.2. Ordre de résolution dans computeLight

Vec3 base = hit.color;
if (m.useImage && m.map && !m.map->empty())
    base = m.map->sample(hit.u, hit.v); // image d'abord
else if (m.useChecker) { /* ... */ }      // sinon damier
// puis éclairage Phase 1 inchangé :
// col = base·(ambient + max(0,N·L)·I·0.9) + ombres dures

L'éclairage et les ombres sont bit-identiques à l'étape 1 quand useImage=false : aucune régression sur uv.rt / exemple.rt. L'image ne touche que base, donc une texture blanche rend exactement comme l'ancien uni blanc — bon test de non-régression.

Pourquoi image > checker ?
Les deux utilisent les mêmes (u,v) : les cumuler (multiplier) assombrirait tout et compliquerait l'évaluation. Priorité simple = prédictible, et tex off / mat diffuse permettent de revenir en arrière.
Thread-safety :
sample() est const, ne fait que lire data. N threads × M pixels lisent la même image sans verrou — comme les Hit locaux de la Phase 1.

5. C'est quoi le .ppm ? (vs PNG/JPG)

fait — détaillé
assets/checker.ppm · assets/checker.png · stbi_load auto-détecte

PPM = Portable Pixmap (Netpbm) : le format image le plus simple qui existe. En-tête texte + pixels bruts :

P6
256 256
255
<196608 octets RGB bruts>
PPM binaire (P6)PNGJPG
ContenuRGB brut, sans compressionRVBA compressé sans pertecompressé avec pertes (photo)
Taille 256×256193 Ko (toujours w×h×3)869 o (damier) — mesures réellesvariable, ~5–20 Ko
Lisible à la mainoui (généré en 10 lignes Python)non (zlib + filtres)non (DCT)
Pour RTv1debug parfait (pixels exacts)assets finaux (léger)photos (jamais de damier !)

AGENTS.md ne parle que de stb_image.h → sampler2D, sans imposer d'extension : stbi_load détecte le format par la signature du fichier, pas par son nom. Notre load() accepte donc PNG/JPG/BMP/TGA/PPM de la même façon — vérifié : checker.png 256×256 charge et rend PASS.

Choix du projet : générer en .ppm (scriptable sans dépendance, pixels contrôlés au bit près), livrer la scène en .png (scenes/image.rt → assets/*.png). Les .ppm restent en fallback. Ne jamais mettre de JPG pour un damier de test : la compression DCT bave les bords noir/blanc.

6. Parser tex + scène image.rt

fait — détaillé

6.1. Syntaxe (appliquée au dernier objet, comme mat)

sp -2,0.5,0 1 255,255,255
tex image assets/checker.png repeat   # ou clamp, ou sans mode (= repeat)
tex off                               # désactive l'image (retour checker/uni)
cyl 0,0,0 0,1,0 0.5 2 255,255,255
tex image assets/uvgrid.png clamp

Erreurs strictes avec numéro de ligne : tex image sans objet avant, wrap inconnu (tile), fichier introuvable (tex image introuvable 'nofile.png' → parsing refusé, pas de rendu partiel). C'est volontaire : une texture silencieusement absente donnerait un rendu « presque bon » impossible à noter.

7. Debug réel : le rendu tout gris

fait — détaillé
Makefile:58 · tmp/image.png vs headless · à raconter en évaluation

Symptôme observé : le headless (compilé frais en une ligne g++) affichait les textures, mais ./bin/rtv1 scenes/image.rt rendait tout gris (tmp/image.png). Même scène, deux résultats → ce n'est pas la scène, c'est le binaire.

Cause : obj/%.o: src/%.cpp — aucune dépendance headers.
Après l'édition de Material.hpp (+map/useImage), SceneParser.o (09:59) n'a pas été reconstruit : l'ancien parser ignorait silencieusement les lignes tex (directive inconnue = skip), objets restés blancs → gris sous lumière. 
HEADERS = $(shell find include -name '*.hpp' -o -name '*.h')
obj/%.o: src/%.cpp $(HEADERS) | $(SDL_SO)   # Makefile:58 — tout header rebuild tout
make clean && make && ./bin/rtv1 scenes/image.rt  # 1080x720 texturé ✓
Leçon : un rendu uni alors qu'on attend une texture = d'abord ls -l obj/ vs include/, pas les maths d'UV. En évaluation, cite les 3 indices : (1) headless frais OK / binaire KO, (2) SceneParser.o plus vieux que Material.hpp, (3) ancien parser = lignes tex ignorées sans erreur.
