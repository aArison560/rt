1. Pourquoi des coordonnées UV ?

fait — détaillé
Séparer où (géométrie 3D) de quoi (couleur 2D) · Hit include/core/Object.hpp:5

Un point d'impact vit en 3D : hit.point = (x, y, z). Une texture (image, damier, bruit) vit en 2D : (u, v) ∈ [0,1)². La fonction de paramétrisation fait le pont :

\(\Phi : \text{surface 3D} \to [0,1)^2, \quad \Phi(P) = (u, v)\) — puis \(\text{couleur}(P) = \text{tex}(u,v)\).

Concrètement dans RTv1, chaque intersect remplit désormais trois choses : le point, la normale et les UV. Le Renderer n'a plus besoin de savoir si l'objet est une sphère ou un plan : il lit juste hit.u / hit.v et hit.material.

Avant (Phase 1)Après (Phase 2 étape 1)
Hit { t, point, normal, color }Hit { t, point, normal, color, u, v, material }
Couleur uniforme par objetCouleur = fonction(u, v) → damier, puis image, puis bruit
Rien à valider visuellementLe damier prouve que les UV sont corrects (cases carrées, pas de couture béante)
Idée clé : le damier n'est pas un gadget — c'est l'instrument de mesure des UV. Des cases qui s'étirent = paramétrisation fautive. Des cases régulières = feu vert pour coller de vraies images à l'étape suivante.

2. Le Material : albedo, type, damier

fait — détaillé
include/core/Material.hpp:1 · Object::material include/core/Object.hpp:30

2.1. Structure

struct Material {
    Vec3 albedo{255,255,255};  // couleur 1 (0-255, comme avant)
    Vec3 albedo2{0,0,0};       // couleur 2 du damier
    MaterialType type = Diffuse;
    bool useChecker = false;   // false -> rendu Phase 1 identique
    double uvScale = 8.0;      // cases par unité UV
};
enum class MaterialType { Diffuse=0, Metal=1, Dielectric=2 };

albedo = fraction de lumière réémise (ici en 0–255 par compatibilité avec Object::color). type ne sert pas encore : il prépare la Phase 3 (réflexion Metal, réfraction Dielectric) sans re-câbler les structures.

2.2. Où vit le matériau ?

Object::material (1 par objet, initialisé à Material(color)) → copié dans Hit::material à chaque intersection → lu par Renderer::computeLight.

Copie volontaire (pas de pointeur) : le multi-thread lit des Hit locaux, aucun verrou, aucune durée de vie à gérer. Chaque constructeur (Sphere, Plane, Cylinder/Cone/Paraboloid/Hyperboloid) fait material = Material(col) — oublier cette ligne = damier noir/blanc par défaut sur cet objet.

Piège : après toute modification d'un .hpp, lancer make re (pas juste make) : le Makefile ne suit pas les dépendances headers, les vieux .o mélangés au nouveau header produisent un warning ODR/LTO silencieux.

3. UV sphérique : longitude × latitude

fait — détaillé
Sphere::getUV src/core/Object.cpp:29 · appel Object.cpp:22

3.1. Dérivation

On normalise : \(\mathbf{l} = (P - C)/r\), donc \(\|\mathbf{l}\| = 1\). Longitude \(\theta = \mathrm{atan2}(l_z, l_x) \in [-\pi,\pi]\), latitude \(\phi = \arcsin(l_y) \in [-\pi/2, \pi/2]\). On ramène à \([0,1)\) :

\(u = \mathrm{fract}\left(\frac{\theta}{2\pi} + 0.5\right), \qquad v = 0.5 - \frac{\phi}{\pi}.\)

Pourquoi \(\mathrm{atan2}\) et pas \(\arctan(z/x)\) ? Parce qu'\(\mathrm{atan2}\) couvre les 4 quadrants (signe de x et z) — \(\arctan\) seul replierait la moitié arrière de la sphère sur l'avant. Le clamp de \(l_y\) à \([-1,1]\) protège \(\arcsin\) des erreurs d'arrondi (\(\|\mathbf{l}\| = 1.0000000002\) arrive vraiment).

void Sphere::getUV(const Vec3& p, double& u, double& v) const {
    Vec3 l = (p - center) / radius;
    double theta = atan2(l.z, l.x);
    double phi = asin(clamp(l.y, -1, 1));
    u = fract(theta / (2*PI) + 0.5);
    v = 0.5 - phi / PI;
}

4. UV planaire : projection sur la base du plan

fait — détaillé
Plane::getUV src/core/Object.cpp:52

4.1. Dérivation

Un plan infini n'a pas de « tour » à dérouler : on prend les coordonnées du point dans deux axes couchés sur le plan. On fabrique une base orthonormée \((\mathbf{a}_u, \mathbf{a}_v)\) à partir de la normale \(\mathbf{n}\) :

\(\mathbf{a}_u = \mathrm{norm}(\mathbf{n} \times \mathbf{arb}), \quad \mathbf{a}_v = \mathrm{norm}(\mathbf{n} \times \mathbf{a}_u), \quad u = \mathrm{fract}((P-P_0)\cdot\mathbf{a}_u), \; v = \mathrm{fract}((P-P_0)\cdot\mathbf{a}_v),\)
avec \(\mathbf{arb} = (0,1,0)\) sauf si \(\mathbf{n} \parallel Y\) (alors \((0,0,1)\)).

Le vecteur arbitraire évite le cas dégénéré \(\mathbf{n} \times \mathbf{n} = \mathbf{0}\). Le fract carrele le plan à l'infini avec des cases de 1 unité monde — uvScale multiplie ensuite la densité dans le checker.

5. UV cylindrique + caps : le tube et ses couvercles

fait — détaillé
Quadric::getUV src/core/Quadric.cpp:53 · caps Quadric.cpp:100/160/200

5.1. Surface latérale : angle × hauteur

Dans la base locale \((U, dir, V)\) déjà cachée pour la Phase 1 (cachedU/cachedV — zéro coût supplémentaire), on récupère \((x_L, y_L, z_L)\) puis :

\(u = \frac{\mathrm{atan2}(z_L, x_L)}{2\pi} + 0.5 \in [0,1), \qquad v = \begin{cases} \frac{y_L - h_{min}}{h_{max}-h_{min}} & \text{tronqué (cylindre, cône, paraboloïde)} \\ \mathrm{fract}(y_L) & \text{infini (hyperboloïde infini)} \end{cases}\)

C'est le même \(u\) angulaire pour toutes les quadriques (cylindre, cône, paraboloïde, hyperboloïde) : seule la coordonnée \(v\) change selon la troncature. Dérouler un cône ou un cylindre donne le même rectangle — la différence géométrique reste dans l'intersection, pas dans les UV.

5.2. Caps : disques en UV planaire local

Un cap est un disque perpendiculaire à l'axe. On projette sur \((U, V)\) et on normalise par le diamètre :

\(u = \mathrm{fract}\left(\frac{(P-C)\cdot U}{2R} + 0.5\right), \quad v = \mathrm{fract}\left(\frac{(P-C)\cdot V}{2R} + 0.5\right)\) — paraboloïde : \(R\) remplacé par \(a\sqrt{h}, b\sqrt{h}\) (rayon réel au bord).

6. Checker + éclairage : la preuve par le damier

fait — détaillé
Renderer::computeLight src/core/Renderer.cpp:17

6.1. Formule

\(i = \lfloor u \cdot s \rfloor,\; j = \lfloor v \cdot s \rfloor, \quad \text{base} = \begin{cases} \text{albedo}_2 & (i+j)\ \mathrm{impair} \\ \text{albedo} & \text{sinon} \end{cases}\) — puis éclairage Phase 1 inchangé : \(\text{col} = \text{base}\cdot(\text{ambient} + \max(0, N\!\cdot\!L)\cdot I \cdot 0.9).\)

Le bit de parité (i+j)&1 coûte ~1 ns : c'est un ET binaire, pas une division. Les ombres utilisent base aussi (sinon un damier à l'ombre « saignerait » sa couleur éclairée). Quand useChecker=false, base = hit.color : rendu bit-identique à la Phase 1 — c'est la compatibilité ascendante qui permet de merger sans régression.

Lecture du damier :
cases carrées → UV linéaires ✓
cases étirées en v → \(v\) non normalisée (oubli de \(h_{max}-h_{min}\))
moiré lointain → normal (aliasing, pas de bug)
couture verticale → \(u=0/1\), attendue
Coût :
\(+\!2\) doubles dans Hit, \(+\!1\) copie Material (~5 doubles) par intersection.
Négligeable devant le \(\sqrt{\Delta}\) et les 2 produits scalaires de la base locale.

7.1. Directive mat (s'applique au dernier objet)

pl 0,-1,0 0,1,0 200,200,200
mat checker 4 50,50,50      # sol : 4 cases/unité, gris foncé
sp -2,0.5,0 1 255,0,0
mat checker 8 0,0,0         # sphère : 8 cases, rouge/noir
mat diffuse                 # désactive le damier (retour uni)

Ordre imposé : la ligne mat après l'objet (erreur « mat checker sans objet avant » sinon). scale > 0 obligatoire. Cas inconnu (mat marbre) → erreur de parsing avec numéro de ligne, pas de valeur silencieuse.

7.3. UV et transformations : le motif suit l'objet

Toutes les formules utilisent le point relatif à l'objet (point - center, point - pos) et, pour les quadriques, la base locale cachedU/cachedV. Conséquence directe :

Translation (G, translate) : le motif bouge avec l'objet — le damier ne glisse pas.
Rotation (R, setDir) : 1 seul rebuild de la base, le motif tourne avec l'objet.
C'est le comportement attendu façon Blender (UV attachés à la géométrie, pas au monde).
